에이전트가 사용할 수 있는 도구가 늘어나면 모든 도구 설명을 매 요청에 넣기 어렵다. 자연스럽게 현재 질문과 관련 있는 도구만 검색해 프롬프트에 추가하는 구조를 떠올리게 된다.

여기서 가장 위험한 착각은 검색 결과를 곧 사용 가능한 도구 목록으로 보는 것이다. 검색은 관련성을 계산하지만, 권한을 증명하지 않는다.

## 검색 결과가 권한을 넓히는 구조

다음과 같은 흐름을 생각해 보자.

```python
matches = tool_index.search(query)
visible_tools = [tool for tool in matches if not tool.hidden]
return visible_tools
```

이 구현은 단순하지만 `hidden`이 아니라는 이유만으로 검색된 도구를 노출한다. 사용자의 역할, 실행 환경 또는 제품 정책상 허용되지 않은 도구도 검색 점수가 높으면 프롬프트에 나타날 수 있다.

도구 정의가 프롬프트에 노출되는 것만으로도 문제가 된다. 모델이 실제 호출에 실패하더라도 내부 기능의 이름과 입력 스키마를 이미 보았기 때문이다. 실행 시점의 권한 검사만으로는 이 노출을 되돌릴 수 없다.

## 권한을 먼저 고정한다

안전한 순서는 반대다.

```python
authorized = policy.allowed_tools(principal, profile)
deferred = [tool for tool in authorized if tool.exposure == "deferred"]
matches = tool_index.search(query, corpus=deferred)
return registry.schemas(matches)
```

먼저 서버가 신뢰하는 정보로 허용 집합을 만든다. 검색 인덱스는 그 집합 안에서만 후보를 좁힌다. 검색 점수나 모델의 요청은 허용 집합을 확장할 수 없다.

이 구조의 핵심 불변식은 하나다.

> 검색은 이미 허용된 도구의 노출 시점만 바꿀 수 있고, 새로운 권한을 만들 수 없다.

## 노출 등급도 권한과 다른 축이다

허용된 도구라고 해서 항상 프롬프트에 넣어야 하는 것은 아니다. 예를 들어 도구를 다음처럼 나눌 수 있다.

- `core`: 매 요청에 항상 노출한다.
- `deferred`: 관련성이 있을 때 검색으로 승격한다.
- `internal`: 모델에게 직접 노출하지 않는다.

이 분류는 컨텍스트 비용을 관리하기 위한 정책이다. 누가 도구를 사용할 수 있는지를 결정하는 권한 정책과 목적이 다르다. 두 축을 하나의 `visible` 플래그로 합치면 비용 최적화와 보안 판단이 같은 조건문에 얽히기 쉽다.

## 복원 데이터는 서버가 소유해야 한다

대화가 이어질 때 이전 턴에 노출했던 도구를 복원해야 할 수도 있다. 이때 클라이언트가 보낸 도구 스키마를 그대로 신뢰하면 권한 경계가 다시 열린다.

클라이언트에는 도구 식별자처럼 검증 가능한 최소 정보만 남기고, 실제 스키마는 서버 레지스트리에서 다시 조회하는 편이 안전하다. 복원할 때도 현재 사용자의 허용 집합과 교집합을 계산해야 한다.

## 최소한 확인해야 할 테스트

관련성 검색의 품질만 측정해서는 이 구조를 검증할 수 없다. 다음 조건을 별도로 확인해야 한다.

1. 관련성이 높아도 권한이 없는 도구는 검색 결과와 프롬프트에 나타나지 않는다.
2. 허용됐지만 관련성이 낮은 지연 도구는 자동으로 승격되지 않는다.
3. 핵심 도구는 검색 결과와 무관하게 유지된다.
4. 검색 대상이 비어 있어도 이전 검색 결과가 다시 사용되지 않는다.
5. 클라이언트가 임의의 도구 식별자나 스키마를 보내도 서버 레지스트리 밖의 도구는 복원되지 않는다.

검색 품질 평가는 이 테스트를 통과한 다음에 해야 한다. 보안 경계가 고정되지 않은 상태에서 재현율을 높이면, 허용되지 않은 도구를 더 잘 찾아주는 시스템이 될 수 있다.

## 공개 전 보완할 내용

- 공개 가능한 합성 도구 목록으로 실패 사례를 재현한다.
- 전체 도구 노출과 검색 기반 노출의 컨텍스트 크기를 비교한다.
- 키워드 검색과 의미 검색의 품질 및 지연 시간 측정 방법을 추가한다.
