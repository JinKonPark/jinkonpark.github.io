독자가 글을 읽고 얻게 될 구체적인 결과나 실패 사례로 시작한다.

## 문제

관찰한 현상과 제약을 적는다. 내부 프로젝트명, 티켓 번호, 고객 정보는 사용하지 않는다.

## 처음 시도한 접근

선택한 이유와 실제로 문제가 된 지점을 코드 또는 작은 예제로 보여준다.

## 바꾼 설계

핵심 경계와 불변식을 설명한다. 구현 세부사항보다 다른 시스템에도 적용할 수 있는 판단 기준을 남긴다.

## 검증

실행한 테스트, 측정 조건, 결과를 구분해서 적는다. 측정하지 않은 수치는 만들지 않는다.

## 한계

검증하지 못한 조건과 다음에 확인할 내용을 적는다.

## 공개 전 점검

- [ ] 회사, 조직, 고객, 동료를 식별할 수 있는 정보가 없다.
- [ ] 내부 티켓 번호, URL, 환경변수, 모델 ID가 없다.
- [ ] 로그, 스크린샷, 코드에 비밀정보가 없다.
- [ ] 업무 코드를 복사하지 않고 공개용 예제로 다시 작성했다.
- [ ] 사실, 추론, 미검증 가설을 구분했다.
- [ ] 링크와 코드 블록을 로컬에서 검증했다.
